## 二、規則

1. 沿用第 1 輪的規則：
   - 不編造；
   - 證據要寫 `檔案:行號` 加上識別字；
   - 無法驗證的標 N/V，N/V 權重超過 20% 就是「部分審核」；
   - 不能提違反 `AGENTS.md` 的建議；
   - 不改程式、不開 PR 或 issue；
   - 跑測試產生的 `docs/` 變更要還原；
   - 用繁體中文。
2. 執行與驗證步驟與第 1 輪提示第三節相同：跑 `npm test`、`npm run music:check`、Playwright 腳本，桌機與手機截圖，跑 Lighthouse，解析 MIDI。A–H 八項全部評分。萬一某一步在你的環境意外失敗，只把受影響的項目標 N/V，並寫明失敗的指令與錯誤訊息。
3. 上次報告裡的**每一個**項目都要逐條核對。commit 訊息寫「已修」不算數，要看程式、跑測試，或對照驗收標準確認。
4. 狀態只用以下四種：
   - **完成**：所有驗收標準都符合；
   - **部分完成**：有些驗收標準符合、有些不符合，請寫出缺哪一條；
   - **未完成**：沒有改，或改了但核心問題還在；
   - **無法驗證**：寫明需要什麼環境才能驗證。
5. 檢查有沒有退化，特別注意：
   - 骨幹契約（MORPH／GENERATE／RESTORE）；
   - 調性判定；
   - MIDI 輸出（同一個輸入，前後的位元組是否相同，或差異是否合理）；
   - 舊存檔遷移（`khimaira-v3/v4/v5`）；
   - 共用核心（`npm run music:check`）。
   退化問題標【退化】，至少列為 P1；如果造成錯音、錯調或資料遺失，就是 P0。
6. 分數變化必須有新證據。沒有新證據就維持原分數。
7. 新問題的編號接著上次的最大編號往下（例如上次最大是 R01-P1-4，新的 P1 就是 R01-P1-5），不要重排舊編號。
